# Order WhatsApp history (RoboDesk)

## Admin setup

Open **التكاملات → إعدادات محادثات واتساب** (`/admin/robodesk/conversation-settings`).
Requires `robodesk.manage`. Enter the dedicated RoboDesk integration user's email/password, choose 1–50 recent conversations (default 20), and enable reading.
The password input is always empty on subsequent visits; leaving it empty preserves the saved password. Disabling integration preserves the history. Email/password use Laravel encrypted casts in a separate settings table and are excluded from JSON and credential-save audit payloads. Preserve `APP_KEY` when migrating/backup-restoring. Do not put credentials in Git, browser JS, generated files or logs.

Message viewing requires an active admin account with **both** `orders.view` and `orders.conversations.view`. Without `orders.conversations.view-all`, access is restricted on every history/sync/read/reply request to active checkouts currently assigned to that employee through `order_group_assignments.assigned_to_user_id`. Managers with `view-all` can also manually inspect historical conversations. Notifications cover all active orders for `view-all` users (including unassigned and other employees' orders); other employees see only their assigned active orders. Assignment is checkout-level, so a cancelled constituent does not block another active constituent of the same assigned checkout. Deleted orders cannot be opened.

`orders.conversations.reply` is a separate permission for sending; read access never implicitly grants it. The new migration grants reply/view-all only to existing active direct permission managers. Grant the appropriate combination explicitly to employees through Admin permissions. Existing custom roles are not reset. New customer-service role defaults retain read permission only.

## API and synchronization

Server-only HTTPS request to the fixed RoboDesk host:
`GET https://hero-kid.robodesk.ai/api/conversation/messagesByPhone`.
Always sends digits-only international `phone`, `channel=WhatsApp`, and configured `limit`. Stored Egyptian local mobiles normalize using the existing Egyptian phone convention; other international numbers retain their country code. Invalid numbers stop locally. No name/gender inference, no browser-supplied phone.

Authorization is the supplied legacy base64 format, **not** Bearer. Password hashing reproduces JavaScript signed 32-bit arithmetic and UTF-16 code units. It is temporary pending a dedicated integration key; the adapter isolates future auth changes. Existing events/webhook/payment integration remains unchanged.

- Panel opens: read the DB cache immediately, then asynchronously request a full sync.
- Visible, expanded panel: background sync every 15 seconds using encrypted stored `after` (remote newest-message ID).
- Empty delta preserves the cursor; messages repeated at the cursor are deduplicated by remote ID.
- Live RoboDesk can also return `direction=system` / `type=systemLog`, contrary to its initial contract. Only this exact pair is excluded from display/storage; other malformed or unknown records still reject the entire page atomically. The cursor uses the last raw record ID, including a filtered log, so a log-only delta does not repeat forever. IDs remain validated and encrypted; no system-log text or attachments are persisted.
- Verified legacy histories can contain an empty pending text placeholder: explicit null `direction` and `date`, `channel=WhatsApp`, `type=text`, `status=pending`, exact empty text and attachment array, and no filename. Only that shape is ignored after validating its ID and the page's customer phone; its raw ID can still advance the cursor. Any content, attachment, filename, known direction, date, other status/type/channel or invalid ID still rejects the page atomically. No invented date/direction and no valid message is deleted.
- Provider 400 with `after`: retry once without it; reset the cursor even if the fallback is empty.
- `senderType` is opaque, inert provider metadata, preserved verbatim up to 64 characters (or null); it does not grant permissions or control execution. The API validator and persistent column share this bound. Longer/non-string values reject the page atomically without advancing its cursor.
- Opening again/manual Refresh requests full recent history, including delivery/text edits. Incremental responses cannot detect edits to older messages not returned by RoboDesk.
- Closing/minimizing stops browser history polling and aborts pending history requests; background tabs do not poll. Window identities and minimized states survive refresh, admin navigation and browser reopening on the same browser. Only `{orderId,minimized}` is stored, names/messages/attachments/signed URLs/credentials/drafts never are. Storage is versioned, bounded to 50 descriptors, isolated by employee and account, safely handles malformed/blocked storage, clears on logout, and reauthorizes every restored order. Unauthorized/deleted windows are removed. Private browsing/storage clearing naturally loses window state.
- Minimized panels become compact circular bubbles on the left with reopen/close buttons and a hover/focus preview; the provider supplies no customer avatar, so use the existing generic user icon, not invented customer photographs. Clicking the expanded header minimizes it; the separate order link and close control retain their independent actions. No visible “تصغير” label. Names display the first eight graphemes with the complete name available in the tooltip; the real checkout reference is linked to authorized order details.
- Windows anchor at the bottom LEFT and extend rightward; desktop space excludes the right admin sidebar. Individual conversation content stays RTL.
- Per-contact 30-second distributed lock and 12-second successful-sync cooldown avoid concurrent or duplicate polling. Slow/failing calls have bounded timeouts (3-second connect, 8-second total per attempt; invalid cursor adds at most one attempt).

Admin endpoints:
`GET /admin/orders/{order}/whatsapp-conversation` reads cache only, never creates history or calls the provider.
`POST /admin/orders/{order}/whatsapp-conversation/sync` fetches and atomically persists validated responses. CSRF, authentication, permission checks and per-user throttle apply. Optional `full=1` drops `after` for that call. A `before` local message ID pages older **saved** history (50 per page); this is not a RoboDesk paging parameter. Cross-contact cursors cannot expose another contact's messages. No mutation of assignments, order status, payments, items, production files or shipping.

## Sending text, emoji and images

`POST /admin/orders/{order}/whatsapp-conversation/reply` requires CSRF and all read/scope permissions plus `orders.conversations.reply`; limited to 20 sends/minute per authenticated user (shared view limit also applies). Multipart fields: UUID `request_id`, optional `text` (4096 characters), optional `image` (real JPEG/PNG/WebP, at most 5 MiB and 12000×12000 pixels). Blank text requires an image. No browser-supplied phone, channel or attachment URL is accepted. The server derives the exact order customer's canonical phone and sends one JSON POST to the fixed RoboDesk `/api/conversation/messagesByPhone/reply` endpoint with the same server-only credentials. Emojis are ordinary text; no third-party emoji service is involved.

The latest saved inbound **non-reaction** customer message must be less than 24 hours old and not future-dated; both UI and server enforce it. RoboDesk remains authoritative: `WINDOW_CLOSED`/`NO_OPEN_CONVERSATION` can still reject a locally eligible reply. Show its plain-text `message` for documented refusals; never use HTML. Outside the window show that a WhatsApp template is required, with template support explicitly pending, not a fake template-send action.

Record a durable UUID operation before contacting WhatsApp. A repeated UUID cannot send again, and a UUID with changed content/user/order/contact is rejected. Only accepted outbound messages appear in history; no optimistic fake sent bubble. A timeout, malformed acceptance, or persistence failure after remote acceptance is `SEND_UNCERTAIN`: keep the draft, do not retry automatically, and require the employee to inspect refreshed history before making another intentional send. A successful HTTP response means accepted, not delivered/read. The operation ledger records employee ID and encrypted name; accepted history also records them, retained through later provider status updates. Sending does not assign a RoboDesk conversation or alter HeroKid order/employee/payment/printing/shipping state. Acceptance never advances the history cursor past unseen inbound messages.

Uploaded reply images are independent temporary copies on `config('media.private_disk','local')`, under `robodesk/replies/{request_id}.{ext}`. An HTTPS-only Laravel signed capability URL allows WhatsApp to download just this explicitly uploaded copy for 24 hours; unsigned, modified and expired URLs fail, and the bucket remains private. It is streamed using the actual stored disk without local-path assumptions. Known failed sends remove their copy; uncertain sends retain it until expiry. `robodesk:cleanup-reply-media` runs hourly and deletes only expired reply copies (bounded 500/run), preserving the audit rows and all order/customer/Media Library originals. These are transport copies, not a reinstatement of historical order-photo retention deletion. Signed URLs are not persisted in message history/browser storage. Provider attachment URLs remain transient as before. No automatic real-customer send is performed during testing.

## Awaiting-reply header notifications

`GET /admin/orders/whatsapp-conversations/notifications` reads saved history only, returning an exact distinct-contact **awaiting-reply** count and the latest 20 contact/order entries, each with a per-employee `unread` flag. It never calls RoboDesk or marks messages read. `view-all` users see all active contacts, including unassigned orders; own-only employees see only assigned active contacts. Both use the Admin order list's active lifecycle: cancelled, fully finished and deleted orders do not notify. Several orders for the same customer count as one conversation. The UI checks this endpoint every 30 seconds only while its admin tab is visible; actual remote discovery follows the worker schedule below.

Reading alone does not remove a pending conversation. A saved successful human outbound reply after the customer's latest non-reaction message dismisses it for everyone; any later customer message brings it back. Human replies include HeroKid sends with recorded employee metadata and synced RoboDesk `senderType=agent` replies. Bot/AI/campaign/automatic-integration replies, reactions, known failed deliveries and failed/uncertain sends without a verified reply never dismiss it. Timeline order uses millisecond `sent_at`, then saved ID for ties, matching the displayed history and conservatively keeping later-discovered same-time customer messages pending. Images sent by an employee count as a response too. A pending conversation can be outside the WhatsApp 24-hour reply window; it remains visible, but the existing send guard still applies. No new migration or environment variable is required for this scope/pending-state change.

New saved inbound IDs increment a contact's `inbound_version`; duplicate IDs, outbound sends and status edits do not. `POST /admin/orders/{order}/whatsapp-conversation/read` acknowledges the displayed `version` for the current employee, not all employees. GETs, minimized restoration and polling alone do not acknowledge. Opening/clicking a visible expanded conversation acknowledges loaded messages. Persist a monotonic per-employee watermark; reject future versions. A new inbound message arriving after the loaded version remains unread. Reassignment is rechecked immediately at every API request. Restored windows cannot retain access after reassignment.

Reply-window presentation distinguishes initial loading, absent history, failed refresh, successfully loaded history with no inbound messages, unverifiable timestamps and an actually expired stored window. A failed/absent sync is never presented as proof that WhatsApp's 24-hour window expired. Existing valid recent inbound history remains eligible; the server and RoboDesk still enforce eligibility and no automatic send/retry is introduced.

## Bounded background refresh / hosting setup

The scheduler runs `robodesk:sync-active-conversations` every minute. It selects only due active contacts (minimum interval 600 seconds), scans at most 100 order rows and queues at most 20 contact jobs per pass, using a fair rotating cursor and deduplicated unique contact jobs. Queue `robodesk-conversations` is separate from general work. The jobs recheck active lifecycle/current phone/account/configuration/due time; call the existing encrypted `after` cursor synchronization; serialize account requests and cap background calls at 20/minute. Provider failures back off for 10 minutes; authentication failures pause the account for 10 minutes. Logs contain sanitized codes/order IDs only. Disabled integration or a `sync` queue connection queues nothing. Larger queues can take longer than 10 minutes to refresh every contact; this is a minimum due interval and bounded target, not an unbounded simultaneous sweep. Web requests never perform the background sweep.

No new environment variables are required. Keep the existing database queue and scheduler. On Hostinger, ensure the existing every-minute scheduler is enabled (do not add a duplicate), and a worker consumes `robodesk-conversations`, for example:

```sh
/usr/bin/php /home/u470070883/domains/hero-kid.com/public_html/artisan schedule:run
/usr/bin/php /home/u470070883/domains/hero-kid.com/public_html/artisan queue:work database --queue=robodesk-conversations --stop-when-empty --max-time=50 --timeout=25 --tries=1 --sleep=1
```

Use hosting process/cron overlap protection for a bounded worker if it is launched every minute. A default-only worker will not consume this dedicated queue. Configure this on deployment; local tests do not configure production hosting. Run normal Composer deployment, `artisan migrate --force`, refresh configuration/routes/views and deploy the committed built assets. The migration is additive (read watermarks, employee reply metadata/operation ledger, permissions); preexisting cached inbound history starts unread, not silently acknowledged. Preserve `APP_KEY`. Do not reset system roles or grant all permissions indiscriminately.

The existing Hostinger setup is documented as `/home/u470070883/run-herokid-queue.sh` calling `schedule:run` and consuming `default`. Check the actual server wrapper and Cron Jobs before changing it; do not duplicate `schedule:run` or replace its existing default worker. If no existing worker consumes `robodesk-conversations`, add one separate every-minute cron, with its own overlap lock:

```cron
* * * * * flock -n /home/u470070883/hero-kid-conversations-worker.lock /usr/bin/php /home/u470070883/domains/hero-kid.com/public_html/artisan queue:work database --queue=robodesk-conversations --stop-when-empty --max-time=50 --timeout=25 --tries=1 --sleep=1 >> /home/u470070883/domains/hero-kid.com/public_html/storage/logs/robodesk-conversations-worker.log 2>&1
```

Confirm `command -v flock` succeeds first. In Hostinger's Cron Jobs UI choose every minute and paste only the command after the five schedule fields. If the existing scheduler is absent, enable it once; the new dedicated worker alone does not dispatch refresh jobs. `QUEUE_CONNECTION=database` and a shared locking cache are already required by the existing setup; no new credentials/env settings are introduced.

Signed attachment URLs exist only in the live HTTP response/browser memory; never in DB, cache, audit or logs. Persistent attachment metadata contains the supplied filename only. Image links can render inline, other files open by an HTTPS link. Expired or unsigned attachments require manual full refresh; old attachments outside RoboDesk's recent-conversation limit may no longer be available remotely. Messages are plain text (`textContent`), not executable HTML. No arbitrary host/URL settings or server-side attachment fetching.

Messages/phone/cursor/sender name/attachment metadata are encrypted at rest. Stable ID hashes support indexed uniqueness and chronological pagination. Provider responses are fully validated before the transactional write; failures preserve old history/cursor. No delete-on-sync, no retention expiry; a message falling outside a recent API window does not remove it from HeroKid. Source interactions/private notes/system logs are not requested separately or fabricated. Multiple orders with the same normalized primary phone share one conversation; different phones remain isolated.
