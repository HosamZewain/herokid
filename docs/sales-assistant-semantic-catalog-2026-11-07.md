# Sales assistant semantic catalog grounding — 7 November 2026

## Problem and behavior

The owner's real conversation received no adventure recommendation and no useful answer about best sellers or offers. Read-only diagnosis confirmed that literal `المغامرات!` returned zero even though15published adventure stories suited a6-year-old girl. The model's candidate set was restricted by that text search before reasoning; adding synonyms alone would preserve that failure mode. The owner explicitly required AI understanding, not literal matching.

The Responses model now receives a broad, compact index of published items eligible for declared age/gender, with actual titles, categories, educational values and description summaries. It interprets the customer's meaning and conversation itself, then may read complete details through existing MCP tools. Its candidate allowance is grounded in this index and validated tool results, not words overlapping the question. The `search_catalog` MCP reader now browses eligible summaries independently of query wording; kind/language/budget/cursor controls remain bounded. A limited index explicitly states total/completeness/next cursor rather than implying the store is empty. The separate manual browsing fallback retains ordinary text search; it is not the model's recommendation gate.

The index adapts summary length within the existing32KB input budget; tool pages retain the12KB conservative serialized bound and four-call cap. A32KB overflow fails before a paid request. No vector store, hosted retrieval service, embeddings model or extra provider call is introduced. Exact `gpt-6-luna`, low reasoning, store:false, queue1worker,USD5/day, reservation/settlement, encrypted retention, usage reporting and private-data rules remain unchanged. [Official tool/MCP reference](https://developers.openai.com/api/docs/guides/tools).

Every turn also supplies ranked public story keys from the existing storefront's recorded-order-quantity source, filtered for the child. It exposes no orders, customer data, quantities, revenue or payment claim. Ranking is cached300seconds; catalog remains60seconds. Public automatic sale prices and conservative package savings use the same native pricing services as checkout; private promotion codes are never queried or listed. `get_store_policies(topic=offers)` exposes only published item keys/conditions. Structured `basis` distinguishes relevance/popularity/offer; the server rejects a purported offer/bestseller absent from those confirmed lists. Cards display the actual regular/current price and offer label. Native checkout still revalidates prices, availability and coupon eligibility. Introduce the assistant only once; known context should lead to a recommendation, rather than another generic discovery question or unsupported team handoff.

Story pricing settings are loaded once per catalog build rather than separately per story. No administration/finance/history/customer-file tool or write authority is added; tool names remain exactly five.
